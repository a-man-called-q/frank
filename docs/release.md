# Frank 1.0 release and recovery

Frank ships a headless backend and a separate Flutter desktop client:

- `frankd`: provider supervisor, SQLite, PTYs, worktrees, Git delivery, and
  the authenticated HTTPS/WebSocket API.
- `frank`: hook fast path, pairing, administration, and per-user service
  control.
- `apps/frank_desktop`: Flutter client with the agent-office shell. It is
  versioned and packaged independently from Cargo.

The client and daemon communicate through the authenticated protocol, including
when both run on one machine. The v1 data/config root is separate from 0.2.x;
an upgrade never migrates or deletes the old data.

## Local release verification

Run these commands from a clean checkout of the release commit:

```sh
cargo test --workspace --locked --no-fail-fast
cargo fmt --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo run --locked -p xtask -- build-packs
git diff --exit-code packs/
cargo run --locked -p xtask -- lint-targets
cargo run --locked -p xtask -- architecture-check
cargo run --locked -p xtask -- version-check
```

When the pinned Flutter 3.47.1 toolchain is available through Proto, run the
client checks separately:

```sh
cd apps/frank_desktop
proto install
proto run flutter -- pub get
proto run flutter -- test
```

The app's first milestone intentionally uses local fixtures. Live transport,
pairing UX, desktop packaging, tray, and single-instance behavior are promoted
only after the fixture shell passes these checks.

## Backend artifacts and recovery

Build backend artifacts and inventory them with:

```sh
scripts/build-release.sh
cargo run --locked -p xtask -- dist
cargo run --locked -p xtask -- checksums
(cd dist && shasum -a 256 --check SHA256SUMS)
```

`frank-update-v1.json` is generated by `scripts/build-update-manifest.sh`. The
script refuses to run without `FRANK_UPDATE_PRIVATE_KEY_B64` and
`FRANK_UPDATE_PUBLIC_KEY_B64`; the private Ed25519 key never belongs in the
repository or CI logs. The detached signature is verified before the manifest
is parsed, and every selected payload is checked for target, size, and SHA-256
digest before staging.

For an offline key ceremony, derive the repository-variable value with:

```sh
cargo run --locked -p frank-release-cli -- public-key --private-key /secure/frank-release.pkcs8
```

Updates are owner-confirmed and never auto-applied. The updater verifies the
signature, target, compatibility range, digest, and package size, retains one
previous stable backend bundle, and rolls back automatically when the restarted
daemon fails its health check. Update state, actor, failure, and rollback are
written to the event and audit streams.

## External release gates

Before calling a build `1.0.0`, run native Flutter smoke tests on every target
that we publish. The gate must cover keyboard navigation, VoiceOver/NVDA
semantics, reconnect after daemon restart, single-instance behavior, and the
Projects/chat/floor surfaces. Backend release checks must also cover fake
provider missions, approval expiry, budget pause, Git conflict, failed delivery
retry, and updater rollback.
